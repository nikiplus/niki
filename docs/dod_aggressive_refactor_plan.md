# Niki 项目 DoD 激进重构总方案

## 0. 定位与边界

本方案以“强 Data-Oriented Design（DoD）”为目标，允许在较长时间窗口内牺牲：

- 运行正确性
- 旧接口兼容
- 短期可发布性

只保留两条硬约束：

- 不丢失已有语义能力目标（语法/IR/执行能力最终要回到或超过当前水平）
- 迁移过程中的每一步都可被代码审阅与后续继续推进（即使暂时不可运行）

---

## 1. 核心设计原则（重构期间的唯一“宪法”）

### 1.1 数据优先于对象

- 禁止“行为绑定数据”的 OO 聚合式扩张（胖类、深层方法链）
- 所有关键阶段以“扁平数据表 + 索引”表达状态
- 面向批处理遍历，不面向单对象消息分发

### 1.2 连续内存优先于指针图

- 用 `std::vector` / 索引 ID 替代裸指针关系
- 跨阶段引用统一为 `u32` 索引（或紧凑句柄）
- 先保证布局稳定，再讨论抽象优雅

### 1.3 管线优先于调用栈

- 编译链路明确拆为 Pass（每个 Pass 输入/输出结构固定）
- Pass 不共享隐式全局状态
- Pass 之间仅通过数据快照通信

### 1.4 可批量验证优先于局部断言

- 结构合法性验证集中化（独立 verify pass）
- 单点函数内“边构建边校验”迁移为“构建后批校验”
- 所有规则可表驱动，不写散落 if-else 规则树

### 1.5 分离“语义正确”与“结构正确”

- 结构规则：引用边界、指令形状、CFG 完整性
- 语义规则：类型匹配、调用签名、可见性、生命周期
- 两者分开执行、分开报告、分开统计

---

## 2. 目标架构（终态）

## 2.1 三层数据域

### A. 前端数据域（Syntax Domain）

- Token 流（SoA）
- AST 节点池（扁平节点 + payload 索引）
- SourceMap（行列/文件偏移映射）

### B. 中间语义域（IR Domain）

- Module 表、Function 表、Block 表、Inst 表、Value 表（全部索引化）
- 引用关系仅允许 ID
- 所有动态扩展字段通过 side-table 管理

### C. 执行域（Runtime Domain）

- 字节码 chunk 池
- 常量池（分区：数值/字符串/符号）
- 执行帧与寄存器窗口（连续布局）

## 2.2 Pass 总线（统一调度）

统一定义：

- `PassInput`：只读视图
- `PassOutput`：新增或替换的数据表
- `PassReport`：诊断与统计

调度器能力：

- 固定拓扑执行（无递归互调）
- 开关化执行（可只跑指定 pass）
- 对每个 pass 记录耗时、输入规模、输出规模

---

## 3. 现状判断与起步模块选择

以当前代码结构看，最优先切入 `l0_core/ir`，并按顺序推进：

1. `verify`（第一刀）
2. `builder`（第二刀）
3. `lower_to_chunk`（第三刀）
4. `vm`（最后替换）

原因：

- `verify` 本身就是批扫描逻辑，最接近 DoD 形态
- `builder` 当前有流程边界（statement/expression 分文件），可继续数据化
- `vm` 耦合运行时行为，放最后可避免早期陷入调试泥潭

---

## 4. 激进迁移路线图（允许阶段性不可运行）

## 阶段 0：冻结旧路径（1-2 天）

目标：为破坏式迁移清场。

动作：

- 标记旧路径为 `legacy`（命名层面即可，不要求移动文件）
- 新建迁移主线文档与 TODO 看板（按 pass 切片）
- 明确“重构期间不保证端到端输出正确”

产物：

- `docs/dod_aggressive_refactor_plan.md`（本文件）
- `docs/dod_migration_todo.md`（后续细化）

---

## 阶段 1：IR 存储重排（5-10 天）

目标：从 AoS（结构体嵌套）向“准 SoA / 表驱动”过渡。

关键改造：

- 将 `IRInst` 访问由“嵌套 vector 逐层跳转”改为“扁平指令池 + block range”
- 为 `Function` / `Block` 建立紧凑元数据表（起始偏移、长度、flags）
- `IRValue` 的 kind + payload 统一进并行数组（可先保留兼容包装）

建议数据布局（示意）：

```cpp
struct InstTable {
  std::vector<uint8_t> kind;
  std::vector<uint32_t> dst_kind;
  std::vector<uint32_t> dst_payload;
  std::vector<uint32_t> a_kind, a_payload;
  std::vector<uint32_t> b_kind, b_payload;
  std::vector<uint32_t> c_kind, c_payload;
  std::vector<uint32_t> aux;
};
```

可接受破坏：

- `dump` 输出顺序短期变化
- 旧 helper API 大面积失效

---

## 阶段 2：verify 规则表化（4-7 天）

目标：从分支逻辑迁移到“规则描述 + 通用执行器”。

关键改造：

- 建立 `InstructionRuleTable`：每个 `IRInstKind` 的操作数约束、终结符属性、引用类别
- `verifyInstructionShape` 改为查表执行
- 引用检查批处理化（一次扫描中聚合统计）

规则表示例（示意）：

```cpp
struct OperandRule {
  bool dst_must_be_vreg;
  ValueKindMask a_allowed;
  ValueKindMask b_allowed;
  ValueKindMask c_allowed;
  bool is_terminator;
};
```

附加目标：

- 报错从“即时 push”改为“错误码 + 参数”延迟格式化
- 支持按错误码聚合统计（便于重构期间观察问题分布）

---

## 阶段 3：builder 管线化（7-14 天）

目标：拆掉“上下文对象 + 递归控制流拼装”中不利于批处理的部分。

关键改造：

- 将 builder 拆成多 pass：
  - Pass A: AST -> Symbol Skeleton
  - Pass B: AST -> Block Skeleton
  - Pass C: AST -> Inst Fill
  - Pass D: CFG Patch（break/continue/backpatch）
- `FuncBuildCtx` 缩减为纯 ID 记录，不持有复杂临时容器
- `local_reg_by_name_id` 分离为符号解析表，不与发射流程耦合

迁移策略：

- 第一版允许“重复扫描 AST 多次”，先换结构再做性能
- 暂时放弃局部最优发射顺序，优先形成可验证数据形状

---

## 阶段 4：IR -> VM lowering 重构（5-10 天）

目标：把 lowering 做成纯数据变换，不依赖 builder 内部假设。

关键改造：

- 引入中间 `LowerWorkSet`（每个函数独立）
- 跳转修补改为集中 patch pass，不在发射时反复回填
- 常量池写入改为去重批量策略（按函数/模块分区可配置）

可接受破坏：

- 字节码布局变化（只保证语义最终等价，不保证字节级一致）
- 旧单测中依赖具体布局的断言需要重写

---

## 阶段 5：VM 执行核重排（10-20 天）

目标：将解释执行核心进一步 DoD 化。

关键改造：

- 指令译码数据分离（opcode stream + operand stream）
- 分离热路径和冷路径（错误处理/日志/调试）
- 调用帧结构压缩（把运行时必需字段放热区）

方向建议：

- 先实现“可跑但未优化”的新执行核，再替换旧核
- 可并存 `vm_legacy` 与 `vm_dod`，由编译开关切换

---

## 阶段 6：删旧与收口（3-7 天）

目标：移除 legacy 分支，统一到新模型。

动作：

- 删除旧 builder/verify 辅助函数
- 删除仅为兼容临时引入的桥接结构
- 文档、测试、诊断输出格式统一

完成标志：

- 新主线默认开启
- 旧路径完全移除

---

## 5. 目录与命名建议（重构期间）

建议新建：

- `include/niki/l0_core/ir2/`（新 IR 数据模型与 pass 接口）
- `src/l0_core/ir2/`（新实现）
- `test/ir2/`（新测试）

为什么建议 `ir2` 而不是原地改：

- 激进改造阶段会产生大量不兼容改动
- 双轨并行可减少“半成品污染主路径”
- 完成后可整体 rename 回 `ir`

---

## 6. 测试策略（允许短期失败，但要有可见进度）

## 6.1 分层测试替代端到端依赖

- L1: 数据结构测试（表长度、索引合法、压缩布局一致）
- L2: pass 测试（输入快照 -> 输出快照）
- L3: 结构验证测试（错误码集合断言）
- L4: 最小运行回归（最后阶段再恢复）

## 6.2 快照基线策略

- 为 `verify report` 引入稳定快照（错误码序列 + 定位）
- 为 `dump module` 引入结构快照（不比较地址、不比较随机顺序）

## 6.3 重构期间 CI 规则

- 允许标记 `expected-fail` 测试集
- 但必须要求“失败数量不可无上限增长”
- 每周至少清理一批 `expected-fail`

---

## 7. 里程碑与验收（以结构完成度为主）

## M1：IR 数据表化完成

验收标准：

- 关键表（func/block/inst/value）可独立遍历
- 旧 API 可失效，但新 API 文档齐全

## M2：verify 全量规则表化

验收标准：

- `verify` 主流程不再包含大量按指令硬编码 switch
- 错误码统计可输出

## M3：builder 管线化

验收标准：

- 具备可观测 pass 边界
- break/continue/branch patch 由专门 pass 负责

## M4：lowering 与 vm 新核接通

验收标准：

- 至少一组最小样例可跑通（哪怕语义覆盖有限）
- 运行链路从 `ir2` 到 `vm_dod` 不依赖 legacy

## M5：删旧收口

验收标准：

- legacy 删除
- 文档、测试、命名统一

---

## 8. 风险清单与应对

### 风险 A：重构期失去方向，陷入“永远在迁移”

应对：

- 每阶段必须定义“可交付产物”（代码 + 文档 + 最小测试）
- 每周强制里程碑复盘

### 风险 B：规则迁移后误报/漏报激增

应对：

- 保留旧 verify 报告做对比（仅过渡期）
- 用错误码 diff 报表跟踪偏差

### 风险 C：性能先降后升期间影响判断

应对：

- 在 M3 前不做性能结论
- M4 后再做 profile 与热点优化

### 风险 D：团队理解不一致导致风格回潮

应对：

- 设立 DoD 代码评审清单（见下一节）
- 新增代码若引入反向 OO 耦合直接拦截

---

## 9. 代码评审清单（DoD 专用）

每个 PR 至少回答：

- 数据是否以连续结构存放？
- 是否通过 ID 关联而非指针链？
- 是否存在不可见共享状态？
- 是否把规则放进表，而非散落分支？
- 是否可批处理遍历并统计？
- 是否给出迁移期可观测指标？

任一关键项回答为“否”，默认不合并。

---

## 10. 建议的首批执行任务（按优先级）

1. 创建 `ir2` 最小骨架（数据表 + 空 pass 接口）
2. 将 `verify` 的终结符规则迁移为规则表
3. 将操作数 kind 校验迁移为规则表
4. 引入 `VerifyIssue` 延迟格式化通道
5. 新建 `test/ir2/verify_rule_table_test.cpp`
6. 补充迁移文档：旧字段到新表的映射关系

---

## 11. 最终说明

这是一份“可破坏、强迁移、以结构演进为中心”的方案。  
短期内项目可以不正确、不可运行、不可发布；但每一步都应把系统推向更高的数据局部性、更清晰的 pass 边界、更可验证的规则系统。  
当你接受这个前提后，`ir -> verify -> builder -> lowering -> vm` 的路径是当前代码库中成本最低、推进最快、收益最大的激进重构主线。
